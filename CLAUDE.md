# Valheim Mods

Each subdirectory is a BepInEx plugin project built with `dotnet build <Project>.csproj -c Release`, or all of them with `dotnet build Valheim.slnx -c Release`.

## Project Structure
- `Directory.Build.props` in the root holds the settings and references shared by every project - a `.csproj` only lists references beyond those, and the assembly name and namespace come from the project file's name
- `Shared\` holds code compiled into every plugin through `Directory.Build.props`, in the `Kriona.Shared` namespace - keep its classes `internal` so each plugin's copy stays its own. `ConfigWatcher` reloads a config file as soon as it's saved: create it in `Awake` with `Config` for BepInEx settings (it reloads without writing the file back unless a value was out of range, unreadable or missing), or with the file's path and a reload callback for a file of the plugin's own, and the plugin's name so it shows "<Name>: config reloaded" on screen (null when the callback shows its own message). It only calls back when the file's contents changed, so a plugin that writes the file outside the callback calls its `Remember` afterwards. A reload callback only reads the file, never writing it back - the user's dedicated server has its config folder linked to the game's, so the two share each file, and a plugin that wrote its own version on every reload would have the other copy read it and write its own in turn, over and over. A file of the plugin's own is written when a world loads, when the plugin finds something new to list, and when an entry changes in Configuration Manager. Call its `Update` from the plugin's `Update` and `Dispose` it in `OnDestroy`
- A plugin with a config file of its own lists its settings in Configuration Manager through `Shared\ConfigMirror`, which binds them as entries in the plugin's BepInEx `Config` with saving turned off - BepInEx's file has the same name and saving would overwrite the plugin's. Set the entries from the file inside `Sync`, which doesn't call back, and write the file in the change callback, then call the watcher's `Remember`. `StateEntries` covers "Prefab = inherit/true/false ## Name" lines
- Since every plugin compiles `Shared\`, it can only use the assemblies `Directory.Build.props` references for all of them - BepInEx, Harmony, the game's and `UnityEngine.CoreModule` - so nothing from `UnityEngine.UI` or TextMeshPro. `ScreenEdge` works out where an arrow pointing at something off screen is pinned and where its label goes, and `ArrowSprite` draws the arrow - CreatureMarker's markers and VikingVillages' speech bubbles both use them. A server turns a joining player away with `ConnectRefusal.Refuse`, which sends the game's ErrorVersion after a reason that any of the mods on the player's side adds to the main menu's "incompatible version" error
- Start a new plugin by copying QuickFill, renaming the `.csproj` and renaming QuickFill to the new name in `Plugin.cs` and `.vscode/tasks.json`, then add it with `dotnet sln Valheim.slnx add <Name>\<Name>.csproj` and to the table in `README.md`
- Each mod has a `README.md` (also used as the Thunderstore README and the Nexus Mods description), a `CHANGELOG.md` with a `## <version>` section per release, a 256x256 `icon.png` and a `thunderstore-categories.txt` with one Thunderstore category slug per line - `build-release.ps1 <Name>` packages the GitHub/Nexus Mods zip and the Thunderstore zip, and `-Publish` releases the version on GitHub, Thunderstore and Nexus Mods, using that section as the release notes and changelog. `-GitHubOnly`, `-ThunderstoreOnly` and `-NexusOnly` publish to just that site
- A mod's `Blueprints\` folder of `.blueprint` files is packaged in both zips beside its DLL. VikingVillages builds village houses from them - the user makes and changes them in game with PlanBuild, as `VikingVillages\Blueprints\README.md` describes, so don't write or edit `.blueprint` files by hand
- ZombieApocalypse and VikingVillages share their viking code through `Shared\Vikings\`, in the `Kriona.Vikings` namespace, which only their two `.csproj` files compile in - so it can use the Unity modules both reference. Each mod builds only its own kind of viking's prefab, and adds what only its kind does to the shared `partial` classes (`VikingCore`, `ServerCheck`, `VikingPrefabPatch`) in a file of its own, like `VikingCoreLiving.cs` and `VikingCoreZombie.cs`. A shared patch acts only on its own mod's vikings, found by its own copy of `VikingCore` - and the prefab checks (`IsLivingViking`, `IsZombieViking`) go by the ZDO's prefab, so each mod knows the other's vikings
- The two mods work without each other, and with any version of each other. Neither references the other's types - they talk only through ZDO keys and item custom data (`ZombieState`, `VikingItems`, `VikingCore.DataKey`), which can never change, and through each mod's public `Link` class, which the other reaches through `ZombieLink` and `VillageLink` by reflection (see `ModLink`), falling back to a default when the installed version doesn't have a method. A new version can add `Link` methods, but never remove one or change its name, parameters or return type - so changing either mod means keeping it working with every released version of the other
- Don't make images - no icons, screenshots, placeholders or README images, whether drawn with a script or any other way. The user makes every `icon.png` and image in `images\`, so leave a new mod without them and say they're still needed
- `stats.ps1` prints each mod's downloads and endorsements on Nexus Mods (v1 API, `NEXUS_API_KEY`) and downloads and likes on Thunderstore (package metrics API, no key), using the links in the root `README.md` table
- `build-release.ps1` and `build-bbcode.ps1` dot-source `release-common.ps1` (the root README table, `.env` secrets, HTTP), `release-thunderstore.ps1` and `release-nexus.ps1`, and `stats.ps1` dot-sources `release-common.ps1`. The Thunderstore team, the BepInExPack dependency and the categories added to every mod (the current game update's and `ai-generated`) are constants at the top of `build-release.ps1`
- Each mod's description in the root `README.md` table summarizes its own `README.md` - when a change adds or alters what a mod does, update its description there too, since it also appears on every other mod's Nexus Mods page, as its Nexus Mods summary and as its Thunderstore description, which allows at most 250 characters
- Every mod's Nexus Mods description ends with an "Other Mods By Me" list that `build-bbcode.ps1` builds from the root `README.md` table, leaving out mods with no Nexus Mods link, followed by the root README's "Other Mods I Use" section. `build-bbcode.ps1 -Publish` pushes the changed descriptions to every mod without a release. The Thunderstore README links to the team's package list instead, since a version's README can't be changed after upload
- `Plugin.cs` holds the `BaseUnityPlugin` with the GUID `kriona.<Name>`, the display name and a version starting at `1.0.0`, and calls `harmony.PatchAll()`
- Harmony patches go in a separate `*Patches.cs` file, one static class per patch
- `assembly_valheim` is referenced with `Publicize="true"`, so private game members can be patched and used directly without reflection
- Look up game code in `external\decompiled\`, which holds `assembly_valheim`, `assembly_utils` and `assembly_guiutils` decompiled one class per file (e.g. `external\decompiled\assembly_valheim\Player.cs`). `external\` is gitignored, so Grep and Glob skip it unless given the folder as their path - search it with `path: external/decompiled`
- Before writing code that does what the game already does for a player (armor, food, skills, rest, weather, picking, crafting), find the game's own version and reuse it: call it, or override the `Character` or `Humanoid` virtual it goes through so the game's callers and other mods see the same result. Copy it only when it can't be reached - kept in `Player`'s private fields, gated on `IsPlayer()`, or messaging the local player or dropping items - and then match its numbers and the world modifiers it reads (`Game.m_foodRate`, `m_skillGainRate`, `m_durabilityRate`, `ScaleDrops`), and say in the docblock which game method it follows
- `external\Valheim\` holds a copy of the game's `valheim_Data\Managed` and `BepInEx\core` DLLs, and `Directory.Build.props` builds against it when the Steam folder doesn't exist, so the mods build on a machine without the game
- `tools\setup-external.ps1` makes both folders, deleting them first, so run it again after a game or BepInEx update. It needs the game with BepInEx installed and ilspycmd (`dotnet tool install -g ilspycmd`). A machine without the game gets `external\` as a copy from one that has it, never through GitHub or anywhere public, since it's the game's code
- Look up how a prefab is built - its hierarchy, components, lights, particle colors, materials and textures - with `python -P tools/prefab-dump.py find|tree|materials|particles <name>`, which finds the prefab's asset bundle itself. It needs UnityPy (`python -m pip install --user UnityPy`), and `-P` rather than `-I` so the user install is found. It reads the asset bundles in the game folder, which `external\Valheim\` doesn't have, so it only runs on a machine with the game installed
- `TweakStats/NAMES.md` is generated from the game's files by `python -P tools/tweakstats-names.py` - run it again after a game update rather than editing the file. Like `prefab-dump.py`, it needs the game installed

## Releasing a New Mod
After making a new mod, end by telling the user these steps for releasing it. Its first release needs a Nexus Mods page that only the website can create, and the scripts can't release it until that page exists:

1. Run `.\build-release.ps1 <Name>` without `-Publish` to write `release\packages\<Name>-<Version>.zip` - it needs the mod's `icon.png`, so the user's icon has to be in place first
2. Create the mod's page on Nexus Mods by hand, uploading that zip as its main file with the version from `Plugin.cs` and that version's `CHANGELOG.md` section. Releases add a version to the mod's one active file, so `-Publish` fails on a page with no file
3. Once the user gives the mod ID, add `[Mod <ID>](https://www.nexusmods.com/valheim/mods/<ID>)` to the mod's row in the root `README.md` table and a Nexus Mods link to the Installation section of the mod's `README.md`
4. Merge the branch into main - `-Publish` and `-GitHubOnly` fail until the release commit is on main, and the branch shouldn't be merged before it has its Nexus Mods link, which is why the Nexus Mods page comes first
5. Run `.\build-release.ps1 <Name> -Publish`. It creates the GitHub release, creates the Thunderstore package with its first upload (at `https://thunderstore.io/c/valheim/p/Kriona/<Name>/`), skips the Nexus Mods upload since that version is already there, and pushes every mod's Nexus Mods summary and description, which adds the new mod to their "Other Mods By Me" lists

Images in a mod's `README.md` only show on Nexus Mods and Thunderstore once the code is merged into main, since the scripts point them at the files on GitHub's main branch. A Nexus Mods description pasted in by hand before then shows broken images until step 5 pushes it again

## Line Endings
- All files use LF, set by `.gitattributes` and `.editorconfig`

## Build Output
- Build output stays in each project's `bin\Release\netstandard2.1\` folder, and a Release build also copies the DLL into `release\dlls\` (the `CopyToReleaseFolder` target in `Directory.Build.props`)
- Don't copy built DLLs into the Valheim `BepInEx\plugins` directory - the user installs mods themselves
- Don't add post-build copy steps or output paths that point at the plugins directory to any `.csproj`
- The user may run several Claude sessions in this repo at once. Hooks in `.claude\settings.json` run `tools\session-guard.ps1`, which denies a `dotnet build` or `dotnet test` while another session is editing code and has the last session to finish build for both. When a build is denied, don't retry it or work around it - tell the user it was left to the other session. Errors in files another session changed are reported to the user, not fixed

## Testing
- The user tests every change in game themselves and knows Claude can't, so don't say a change hasn't been tested in game
- Write unit tests alongside new or changed code where they make sense - math, geometry, parsing, save formats written to ZDOs or player data, tables, rules and time windows - and leave them out for engine glue, Harmony patches and one-liners. A test that finds a bug comes with the fix
- Unit tests for a mod go in `Tests\<Name>.Tests\` (xUnit v3 on .NET 10), run with `dotnet test --project Tests\<Name>.Tests\<Name>.Tests.csproj -c Release`, or every test project with `dotnet test Valheim.slnx -c Release`. `global.json` opts `dotnet test` into Microsoft.Testing.Platform, which xUnit v3 needs. `build-release.ps1` runs a mod's tests after building it and stops on a failure
- `Tests\Directory.Build.props` sets everything up from the project's name - it imports the root `Directory.Build.props` for the game references, references the mod's project, and compiles in `Tests\Shared\`, whose `GameAssemblies` loads the game's and BepInEx's DLLs from the folders the build found them in. A new test project's `.csproj` is just `<Project Sdk="Microsoft.NET.Sdk"></Project>`, added with `dotnet sln Valheim.slnx add`
- Every mod has `InternalsVisibleTo` for `<Name>.Tests`, so tests reach its internal classes and its copy of `Shared\` - make a private helper `internal` to test it. Tests of `Shared\Vikings\` go in `Tests\Vikings.Tests\`, which tests VikingVillages' copy
- Tests run outside Unity, so they can't reach anything that calls into the engine - `Debug.Log`, `Random`, `Time`, `Quaternion.Euler`, `eulerAngles`, `Inverse` and `AngleAxis`, `Animator.StringToHash`, `Shader.PropertyToID`, `Plugin.Log` and config entries, components and game objects. `Mathf`, `Vector2`, `Vector3` and `Quaternion`'s operators are plain C# and work. Touching a class runs its static field initializers, so a class whose statics call the engine (like `VikingPoses`, through `ZSyncAnimation.GetHash`) can't be tested at all. Test the code that works things out - math, parsing, tables and rules - and move logic like that into a helper of its own when it's tangled up with engine calls
